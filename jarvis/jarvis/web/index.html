          🎙️ HA Assist

          Talk to JARVIS through any Home Assistant voice assistant as you would in the Telegram chat: same model, same tools, same conversation history — ask aloud, follow up in the chat, or the other way round. Answers are spoken prose: no icons, links or markup. What the Telegram menu does works by voice too: "run the task Morning weather", "run the thunderstorm risk monitor", "are storms coming?" (/storm), "is it going to rain?" (/rain), "station readings in Naples". Live monitors can speak their alerts: Announce by voice in each live monitor.

          Direct commands — no model, no tokens: rain → /rain · storm → /storm · radar + pioggia/piove/piovere → /rain · radar + temporale/i, fulmine/i → /storm · radar alone → both · sta per piovere → /rain · misura/e, stazione/i, sensore/i → /stations (place after a / di / in / presso / vicino a, else your position). A monitor's name in the sentence narrows to it; otherwise every monitor of that kind answers.

          Home commands stay with Home Assistant: with Prefer handling commands locally on, HA switches "the living room light" itself — instantly, with its own names and aliases — and only what it does not understand reaches JARVIS.

          Setup (once): JARVIS copies its integration into Home Assistant by itself. 1) Restart Home Assistant. 2) Settings → Devices & services → Add integration → JARVIS, with the URL and token from Show URL and token below (if Discovered: JARVIS appears instead, just confirm it). 3) Settings → Voice assistants → your assistant → Conversation agent: JARVIS and turn on Prefer handling commands locally.

          🔌 Providers

          API keys are set in the add-on Configuration tab. Here you set the plan behind each key: JARVIS sizes every request to the tightest of the model's context window and these two limits, for the primary and the fallback provider separately.

          Tokens / min — the rolling 60-second budget, prompt and reply of every round. When a request would not fit in what is left of the minute JARVIS waits; when it could not fit in a whole minute, it trims it first. Max tokens / request — the largest single request, whatever the model allows. 0 = the default shown.

          Cloudflare Workers AI has no per-minute budget: it bills Neurons against a daily allowance (10,000 free, reset at 00:00 UTC; then requests fail until midnight and the fallback answers). A typical turn costs 50–250 Neurons depending on the model, so the 32K per-request default keeps one long page from spending a third of the day. Needs cloudflare_account_id and cloudflare_api_token: dashboard → AI → Workers AI → Use REST API → copy the Account ID, then Create a Workers AI API Token.

          🚗 Car Mode

          JARVIS messages are built to be looked at: an icon on every line, bold text, abbreviated units and, for weather, a radar chart. Behind the wheel that format breaks down — CarPlay announces emoji by name, spells 45° and 2/4 as symbols, reads URLs character by character, and a message with a photo attached is often not read out at all.

          When enabled, every alert, scheduled report and chat answer is rewritten as plain spoken prose: icons, markup and links removed, coordinates and diagnostics dropped, units spelled out (km/h → chilometri orari), compass points expanded (O → ovest), and lines joined into sentences. Charts are not sent. Snapshots you ask for with /rain and /storm keep their picture — you requested those, so you are looking at the screen.

          Nothing that describes the instrument is said at all: no token or tool footer even when those toggles are on, no coordinates, map links or record ids, no fix age, accuracy or “non si sta muovendo”, no radar coverage. But every line that explains a failure survives — a blind monitor and why, a switched-off one, a stale feed. Silence and calm must not sound the same.

          The conversion is deterministic — no model call, no added latency, no tokens spent. Toggle it from Telegram at any time with /car.

          Enabled

          Sends a sample storm alert to your Telegram in Car Mode wording, whatever the toggle above is set to. Listening to it through CarPlay is the only real test.

          Tools

          🌐 URL Fetch

          When enabled, JARVIS can fetch the content of any URL you provide, using Jina Reader (free, no API key required). The raw page text is returned directly to JARVIS — no extra LLM call is made. JARVIS analyses the content with its own model.

          How much of a page survives is decided by the model, not by a fixed number: the text is trimmed to what is left of the context window and of the minute's token budget, and a trimmed page is marked as such so JARVIS reports a partial read instead of filling in the rest. Jina's anonymous tier is rate-limited, so a fetch fails now and then — when it does you get a ⚠️ Telegram notice naming the HTTP status, rather than a summary of Jina's error page.

          Image tags are dropped before the page reaches the model — a page of signed thumbnail URLs costs tokens and says nothing. And Jina decides for itself which part of a page is the content: on a school news archive it kept the month menu and threw away all eighteen headlines. When what comes back is nearly all addresses, JARVIS reads the page a second time as plain text and keeps whichever reading carries more words. That second read costs one HTTP request and no model tokens.

          Sometimes a page is not the thing to read but the way to find it, and that failure looks like nothing at all: pretemp.it serves a home page of perfectly good Italian — so the check above sees nothing wrong — with none of the three links to the day's forecasts that are in its HTML, and no fixed address to reach them by. JARVIS can therefore ask a page for its links instead of its text, filtered to what it is looking for: four lines to choose from, then a second read of the address it picked. A task that must follow a link says so in its own instructions — there is nothing to switch on here.

          MeteoHub — ground stations

          MeteoHub (Agenzia ItaliaMeteo) republishes the Italian ground-station networks — about 5000 stations on a ten-minute cadence, free and without an account. It is the only source in JARVIS that measures rain instead of inferring it from radar reflectivity.

          It is used by rain front monitors to add one diagnostic line naming the station that is actually catching the rain. It changes no decision anywhere — not when an alert fires, not which ring it reports, not when the all-clear arrives.

          Enabled
          Official networks only
          On: regional civil protection (dpcn-*), ARPA FVG, SIR Toscana, Trentino and the Emilia-Romagna networks. Off: also MeteoNetwork, the largest single network in the country at about 1000 stations — better coverage inland, but siting and shielding are not guaranteed and a badly exposed gauge is wrong in a way that looks right.
          How far the /stations command looks. Every value it prints carries the distance of the station that measured it, so a wider radius fills gaps rather than hiding them: around Bari a barometer is 55 km away, in Bologna there is a full weather station at 1 km. This does not affect the monitors — those use their own alert radius.
          Stations publish every ten minutes, so asking faster returns an answer that cannot have changed. This is politeness towards a free public service, not a performance setting.
          Answers with the nearest rain gauge to those coordinates, its network and its distance. A reachable service with no gauge in range is the failure that actually bites — the alert line would read “no station” forever and look like a bug — so this names what it found rather than only saying “ok”. Leave the coordinates empty to test on Rome.

          Data licensed CC BY 4.0 by Agenzia ItaliaMeteo and the network owners. The owning network is named in every line JARVIS prints, which is what carries the attribution.

          ▶ Google OAuth2 setup guide

          No Google username or password is stored — only a free OAuth2 credential is needed. Do Part 1 once (covers both Calendar and Gmail). Then do Part 2 for each service you want to enable.

          Part 1 — One-time Google Cloud setup

          1. Go to console.cloud.google.com → create or select a project.
          2. APIs & Services → Library → search Google Calendar API → Enable.
            Then search Gmail API → Enable.
            (Enable only the ones you need — both are free.)
          3. APIs & Services → OAuth consent screen → choose External → fill in app name (e.g. JARVIS) and your email → save.
          4. Still in the consent screen → Publishing status → click Publish app → confirm.
            ⚠️ This step is essential. If the app stays in Testing mode, Google revokes the refresh token every 7 days and you will need to re-authenticate repeatedly. Publishing makes the token permanent. No Google review is required for personal use.
          5. Credentials → Create credentials → OAuth client ID → Desktop app → any name → Create.
          6. Copy Client ID and Client Secret from the dialog.
          7. Paste them in the app Configuration tab (google_client_id, google_client_secret) → restart the app.

          Part 2 — Authorize Google Calendar

          1. Send /gcalauth to the Telegram bot → click the authorization link it replies with.
          2. Sign in with your Google account → grant access → the browser redirects back to JARVIS automatically ✅.
          3. The bot confirms the connection. Enable Google Calendar above and save.

          If the automatic redirect doesn't work (HA on a different device), copy the full URL from the browser address bar and send it as /gcalauth <url>.

          🏠 MQTT / Home Assistant

          Must match base_topic in your HA mqtt_statestream config.

          📍 Positions

          A position is a phone JARVIS can follow. A Storm front monitor selects one and then watches wherever that phone is, so while travelling it can tell you whether you are driving into the storm rather than away from it. Add one per phone — yours, another family member's — and give each a name you will recognise in an alert.

          How to publish a phone's position to MQTT (Home Assistant setup)

          A device_tracker keeps its coordinates in attributes, and mqtt_statestream publishes states. Rather than turning on publish_attributes — which is global and would flood the broker with every attribute of every included entity — expose just the two values as template sensors, in configuration.yaml:

          template:
  - sensor:
      - name: "Phone latitude"
        unique_id: phone_latitude
        state: "{{ state_attr('device_tracker.my_phone', 'latitude') | round(5) }}"
        availability: "{{ state_attr('device_tracker.my_phone', 'latitude') is not none }}"
      - name: "Phone longitude"
        unique_id: phone_longitude
        state: "{{ state_attr('device_tracker.my_phone', 'longitude') | round(5) }}"
        availability: "{{ state_attr('device_tracker.my_phone', 'longitude') is not none }}"
      - name: "Phone GPS accuracy"
        unique_id: phone_gps_accuracy
        state: "{{ state_attr('device_tracker.my_phone', 'gps_accuracy') | int(0) }}"
        availability: "{{ state_attr('device_tracker.my_phone', 'gps_accuracy') is not none }}"

mqtt_statestream:
  base_topic: homeassistant
  publish_attributes: false
  publish_timestamps: true
  include:
    entities:
      - sensor.phone_latitude
      - sensor.phone_longitude
      - sensor.phone_gps_accuracy

          Repeat the three sensors per phone, with distinct names.

          If you already have an mqtt_statestream block, merge into it — Home Assistant accepts only one, and a second would drop your current includes.

          publish_timestamps: true is worth keeping: it publishes last_updated alongside each value, which is the only way to tell how old the retained position received on connect actually is. Without it a fix from yesterday looks brand new.

          Finally, in the Companion app raise the location update frequency (Settings → Companion app → Manage sensors → Location sensors). The default "significant change" reporting can lag by minutes at motorway speed, which is exactly when this feature has to be right.

          This is what an alert is titled with, so make it recognisable.
          Listens on MQTT for 3 seconds and keeps only what looks like a coordinate, filling in each field when there is exactly one candidate.
          Topic path after the prefix — sensor/phone_latitude means homeassistant/sensor/phone_latitude/state.
          How fresh a fix has to be to be treated as current. Past this the fix is still used — a phone that stops moving stops publishing, so an old fix is usually the evidence that you have not moved — but the alert says so, printing the coordinates it measured from and their age. While a storm is in progress this budget is tripled, so losing GPS in a tunnel does not even count as old.
          Ignored when no accuracy entity is configured.
